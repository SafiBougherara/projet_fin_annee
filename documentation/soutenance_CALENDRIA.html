Pourquoi Scrum plutôt que le cycle en V ?

  • Flexibilité encadrée : le périmètre a dû évoluer (WhatsApp → Telegram) sans casser le planning.

Pourquoi pas de Git Flow ?

Git Flow existe pour synchroniser plusieurs développeurs et permettre la revue croisée. Seul sur le projet, des branches feature/* que je serais le seul à ouvrir, relire et fusionner n'auraient été qu'une cérémonie sans bénéfice. J'ai choisi le trunk-based development : commits petits et fréquents sur main, la CI bloquante jouant le rôle du relecteur.

Convention de commits

<type>: <description>

feat     nouvelle fonctionnalité
fix      correction de bug
docs     documentation
test     tests
chore    maintenance

› feat: add service/opening hours CRUD
› fix: CI DATABASE_URL use 'calendria'
› test: add unit tests for DisponibiliteService
› docs: rapport final Jalon 6

VII — Conception de l'application (UML)
Section VII — Vue dynamique

Séquence : authentification JWT

Le flux en 4 temps

  • Le frontend React envoie POST /api/login (email + mot de passe).
  • Symfony vérifie le hash Argon2id et le rate limiter d'IP.
  • LexikJWT signe un token RS256 avec la clé privée RSA 4096.
  • Chaque requête suivante porte Authorization: Bearer <token> — l'API reste stateless.

Conséquence sécurité

Sans session ni cookie de navigation, l'application est insensible au CSRF par construction.

VIII — Architecture multi-couches
Section VIII — Architecture logique

4 couches backend & principes SOLID

ControllerCouche HTTP
→
ServiceCouche métier
→
RepositoryPersistance
→
EntityModèle Doctrine

Responsabilités

  • Controller : désérialise le JSON, délègue, renvoie un code HTTP typé (201, 400, 401…). Aucune logique métier.
  • Service : DisponibiliteService, ChatbotService, NotificationService — indépendants du contexte HTTP, donc testables unitairement.
  • Repository : toutes les requêtes DQL complexes, jamais dans le contrôleur.
  • Entity : POPO Doctrine, propriétés et accesseurs.

Principes SOLID appliqués

SRP

La séparation Controller / Service / Repository garantit qu'une classe n'a qu'une seule raison de changer.

OCP

Les State Providers / Persisters d'API Platform étendent le comportement sans modifier le cœur.

DIP

Injection de dépendances Symfony : les contrôleurs reçoivent leurs services par constructeur, jamais d'instanciation en dur.

VIII — Architecture multi-couches
Section VIII — Cœur métier

L'algorithme de disponibilité & d'attribution

// DisponibiliteService — logique nominale
1. Restaurant existe ?              → sinon indisponible
2. Date valide & hors fermeture ?   → sinon "ferme"
3. Un SERVICE couvre-t-il l'heure ?  → sinon "ferme"
4. Fenêtre d'occupation =
      duree_repas + buffer_nettoyage
5. Tables libres sur la fenêtre, avec
      capacite >= nombre_personnes
6. Tri par capacite ASC
      → capacité exacte prioritaire,
        sinon table immédiatement supérieure
7. Si aucune table :
      proposer des alternatives par pas de 30 min

Pourquoi ce tri ?

Placer 2 personnes sur une table de 8 gaspille 6 couverts pour tout le service. Le tri croissant sur la capacité maximise le remplissage global tout en garantissant le confort.

Paramètres configurables

duree_repas et buffer_nettoyage sont portés par l'entité RESTAURANT : le restaurateur ajuste son turnover depuis le dashboard, sans redéploiement.

Testé unitairement

4 tests PHPUnit couvrent : restaurant inexistant, aucun service configuré, service ouvert avec table libre, date au format invalide.

Section XIV — Retour d'expérience

5 difficultés, 5 solutions documentées

ProblèmeCause identifiéeSolution retenue
1. CORS en productionURL Railway auto-générée, non connue au build ; sous-domaine modifiable.Variable CORS_ALLOW_ORIGIN en regex, lue à l'exécution par NelmioCors — configuration sans rebuild.
2. Déconnexions à chaque déploiementClés JWT RSA régénérées au build Docker ⇒ tokens existants invalidés.Comportement documenté et accepté pour le MVP ; solution cible : clés en secret Railway montées au démarrage.
3. Container qui plante au bootservices.yaml injectait TELEGRAM_BOT_TOKEN / GEMINI_API_KEY dans tous les services via bind.Valeurs par défaut vides : %env(default::TELEGRAM_BOT_TOKEN)%.
4. CI cassée : base calendria_test_testSymfony ajoute _test quand APP_ENV=test, en plus du suffixe déjà présent dans l'URL.DATABASE_URL pointe vers calendria sans suffixe — Symfony complète tout seul.
5. 502 Bad Gateway sur Railwaynginx écoutait un port codé en dur, Railway impose $PORT dynamique.entrypoint.sh réécrit la conf nginx via sed avant de lancer supervisord.

Chaque incident est traçable dans l'historique Git par son commit de correction, puis documenté dans le rapport final — la démarche de diagnostic compte autant que le correctif.

2. Project Summary

CALENDRIA is an AI-powered, multi-channel restaurant reservation management system. It was designed to address a concrete business problem faced by independent restaurateurs: the time-consuming process of managing phone reservations, estimated at up to two hours per day for a typical restaurant with 40 covers.

Core Features Delivered

  • AI Chatbot (Google Gemini 2.5 Flash) - Understands natural language reservation requests, extracts key information (date, time, party size, name), checks availability in real time, and confirms bookings automatically
  • Multi-channel Access - Web chatbot widget (embeddable via iframe), Telegram Bot (webhook-based), and Retell AI voice agent (phone reservations)
  • Smart Table Allocation Algorithm - Assigns the most appropriate table (matching capacity) and proposes alternative time slots when the requested slot is unavailable
  • Restaurateur Dashboard (React SPA) - Real-time reservation management, interactive floor plan with time slider, full CRUD operations, dark mode
  • Secure REST API (Symfony 6.4) - JWT RS256 authentication, rate-limited login, CORS enforcement, OWASP-compliant endpoints
  • Production Deployment - Fully containerized (Docker + nginx + PHP-FPM), deployed on Railway with automatic CI/CD via GitHub Actions

1.2 Problématique Identifiée

Les restaurateurs font face à plusieurs défis dans la gestion de leurs réservations :

Problèmes Actuels

  • Charge téléphonique élevée : Le personnel en salle doit gérer les appels de réservation pendant le service, perturbant l'expérience client
  • Disponibilité limitée : Impossibilité de prendre des réservations en dehors des heures d'ouverture (matin, après-service, jours de fermeture)
  • Perte de clients : Les clients qui n'obtiennent pas de réponse immédiate réservent chez un concurrent
  • Erreurs de réservation : Risques de double réservation, mauvaise estimation du nombre de couverts, oubli de rappel
  • Gestion complexe des tables : Difficulté à optimiser le remplissage (tables de 2, 4, 6, 8 personnes)
  • No-show : Clients qui ne viennent pas sans prévenir, entraînant une perte de chiffre d'affaires
  • Coût du personnel : Nécessité d'avoir du personnel dédié à la prise de réservations

1.3 Solution Proposée : CALENDRIA

CALENDRIA est un assistant de réservation virtuel basé sur l'intelligence artificielle, conçu pour automatiser la gestion des réservations de tables dans les restaurants.

Fonctionnement Global

  1. Client initie la réservation : Via l'un des canaux disponibles : - 🌐 Widget Web : Chatbot intégré sur le site du restaurant - 📲 Telegram Bot : Message vers le bot dédié - 📞 Agent Vocal IA (Retell AI) : Appel téléphonique géré par IA

  2. Conversation IA : Le chatbot engage une conversation naturelle et collecte : nom du client, numéro de téléphone, nombre de personnes, date et heure souhaitées, demandes spéciales (optionnel)

  3. Vérification de disponibilité en temps réel : consultation des tables disponibles selon leur capacité, vérification des créneaux horaires configurés, application de l'algorithme d'attribution intelligent

  4. Validation automatique : ✅ Si disponible : Réservation confirmée instantanément ❌ Si indisponible : Proposition automatique de créneaux alternatifs

  5. Dashboard restaurateur : visualisation en temps réel de la nouvelle réservation

1.4 Utilisateurs Cibles

Utilisateurs Principaux

  1. Restaurateurs / Gérants - Configurent les paramètres du restaurant (tables, horaires, services) - Consultent les réservations du jour/semaine - Peuvent annuler ou modifier une réservation - Analysent les statistiques de remplissage

  2. Clients - Réservent via Widget Web, Telegram ou agent vocal - Reçoivent des confirmations instantanées - Peuvent annuler ou modifier via le même canal

Utilisateurs Secondaires

  1. Personnel de salle (optionnel) - Consultent les réservations du jour, marquent les clients comme "arrivés" ou "no-show"

1.5 Valeur Ajoutée

  • Disponibilité 24/7 : Les clients peuvent réserver à tout moment, même à 2h du matin
  • Gain de temps : Réduction estimée de 70% du temps consacré à la gestion des appels (source : étude OpenTable 2023)
  • Réduction des erreurs : Automatisation de la gestion des tables et couverts
  • Amélioration de l'expérience client : Réponse immédiate 24h/7j, pas d'attente en ligne
  • Optimisation du remplissage : Algorithme intelligent pour maximiser l'occupation des tables
  • Réduction des no-show : Rappels automatiques et demande de confirmation (objectif : réduire de 25 à 30%)

2. Périmètre Fonctionnel

2.1 Fonctionnalités Principales (IN SCOPE)

2.1.1 Module IA Conversationnel - Multi-Canal

Architecture Partagée : Tous les canaux utilisent la même API REST Symfony, même logique de chatbot (Gemini 2.5 Flash), même algorithme de disponibilité.

Canal 1 : Widget Web (Priorité 1)

Chatbot intégrable sur le site du restaurant via iframe. Conversation naturelle en français, collecte d'informations, vérification de disponibilité, validation automatique.

Canal 2 : Bot Telegram (Priorité 2)

Chatbot via messagerie Telegram. Webhook /api/chatbot/telegram, gestion de session, confirmation automatique. Remplace WhatsApp Business (initialement prévu) sans barrière de paiement.

Canal 3 : Agent Vocal IA - Retell AI (Bonus)

Réservation par téléphone via agent vocal IA. Webhook /api/chatbot/call, messages d'erreur intelligents avec alternatives horaires.

2.1.2 Algorithme de Gestion des Tables

  • Attribution intelligente : Priorité aux tables de capacité exacte, puis table immédiatement supérieure
  • Calcul de disponibilité : Vérification en temps réel selon les services configurés
  • Alternatives horaires : Propositions automatiques par pas de 30 min si créneau indisponible
  • Gestion des contraintes : Délai minimum/maximum, blocage de dates, fermetures exceptionnelles

2.1.3 Interface Restaurateur (Dashboard Web)

Application React SPA avec : authentification JWT, tableau de bord temps réel, plan de salle interactif avec slider temporel, gestion CRUD des réservations, gestion des tables et services, fiche client avec historique, mode sombre persistant.

2.2 Fonctionnalités Hors Scope (OUT OF SCOPE)

  • ❌ Paiement en ligne

  • ❌ Multi-langues (français uniquement)

Section VIII - Architecture Multi-Couches

1. Architecture N-Tiers (Déploiement Physique)

L'application suit une architecture 3-tiers au sens du déploiement physique :

Clarification 3-tiers vs N-couches : L'architecture physique est 3-tiers (navigateur, serveur API, base de données). L'architecture logique interne au backend est N-couches (4 couches : Controller, Service, Entity, Repository).

Tier 1 : Présentation (Client)

Navigateur Web / Mobile : Charge la SPA React compilée par Vite. Fichiers statiques servis par nginx. Gère l'affichage (UI), le routage côté client (react-router-dom) et l'UX.

Tier 2 : Logique Applicative (Backend API)

Symfony 6.4 (PHP 8.4) : Reçoit les requêtes HTTP JSON et les webhooks externes. API RESTful Stateless : authentification via JWT à chaque requête, pas de sessions en mémoire. Configure CORS via NelmioCorsBundle.

Tier 3 : Accès aux Données (SGBD)

PostgreSQL 15 : Base relationnelle protégée du réseau externe, accessible uniquement par le Tier 2 via TCP/IP sur le port interne 5432.

Figure 8.1 - Architecture N-Tiers de CALENDRIA

2. Architecture Logique (Backend Symfony)

Le backend Symfony suit le pattern MVC étendu vers une architecture hexagonale (orientée services) :

A. Séparation en 4 Couches

  1. Controllers (Couche HTTP) : Point d'entrée des requêtes HTTP. Désérialisent les données JSON, appellent les services métier, retournent des réponses HTTP typées (201, 400, 401…). Les endpoints principaux sont des contrôleurs Symfony avec #[Route], offrant un contrôle total.
  2. Services (Couche Métier) : Logique métier complexe - algorithmes de disponibilité (DisponibiliteService), orchestration webhooks (ChatbotService), intégrations API (NotificationService). Indépendants du contexte HTTP.
  3. Entities (Couche Modèle) : POPO (Plain Old PHP Objects) représentant les entités métier. Pas de logique d'infrastructure, uniquement propriétés et getters/setters.
  4. Repositories (Couche Persistance) : Data Access Layer via Doctrine ORM. Les requêtes SQL complexes (ex: réservations du jour) résident dans les repositories, pas dans les contrôleurs.

B. Principes SOLID Appliqués

  • SRP : La séparation Controller / Service / Repository assure qu'une classe n'a qu'une seule raison de changer
  • OCP : State Providers/Persisters API Platform permettent d'étendre le comportement sans modifier le cœur
  • DIP : L'Injection de Dépendances Symfony - les contrôleurs reçoivent les services dans leur constructeur

3. Composants Externes et Bibliothèques

Back-end (Bundles Symfony)

Section IX - Sécurité et Conformité

1. Politique de Sécurité Applicative (OWASP Top 10)

L'architecture de CALENDRIA a été conçue pour respecter rigoureusement les préconisations de sécurité de l'OWASP.

a) Injection SQL (A03:2021)

  • Protection native via l'ORM : Doctrine ORM utilise des requêtes préparées systématiques, séparant hermétiquement la logique SQL des données utilisateur
  • QueryBuilder : Toutes les variables externes ($restaurantId, $dateStr…) injectées via ->setParameter(). Aucune concaténation brute de chaîne tolérée

b) Failles XSS (A03:2021)

  • Échappement automatique React : Toutes les variables dans le JSX sont échappées par défaut, prévenant l'exécution de scripts malveillants
  • Échappement Twig : Pour les pages backend (erreurs, profil), échappement HTML par défaut sur toutes les variables

c) Attaques CSRF (A01:2021)

  • API Stateless avec JWT : Les requêtes du frontend n'utilisent pas de sessions/cookies de navigation, rendant l'application insensible au CSRF
  • Le token JWT est stocké en mémoire React et envoyé dans Authorization: Bearer <JWT_TOKEN>

d) Brute Force (A07:2021)

  • Rate Limiting : LoginRateLimiterSubscriber - 5 tentatives max / 15 min par IP
  • Blocage IP automatique via cache Symfony après dépassement

e) Stockage des Mots de Passe (A02:2021)

  • Argon2id : Algorithme de hachage par défaut de Symfony 6.4 - aucun mot de passe stocké en clair
  • Politique de mot de passe robuste exigée à la création de compte

f) Contrôle d'Accès & Firewalls (A01:2021)

  • Firewall Principal (/api) : Protège tous les endpoints d'administration - JWT valide requis (401 sinon)
  • Firewall Public (/api/chatbot) : Accès public autorisé pour le Widget Web, le bot Telegram et les webhooks - limité aux actions conversationnelles

Situation : Les clés JWT RSA étaient initialement générées localement et risquaient d'être committées par erreur. Solution : Génération des clés directement dans le Dockerfile au build time - les clés ne transitent jamais dans le dépôt Git. Ajout d'un .gitignore couvrant config/jwt/*.pem.

Section XIV - Difficultés Rencontrées et Solutions

Le développement de CALENDRIA a confronté plusieurs obstacles techniques significatifs. Chaque problème a été une opportunité d'apprentissage et a conduit à une solution documentée.

Problème 1 - Configuration CORS en Production

Symptôme : Les requêtes du frontend vers le backend échouaient avec l'erreur CORS policy: No 'Access-Control-Allow-Origin' en production.

Cause : L'URL du backend Railway (auto-générée) ne correspondait pas à la configuration CORS statique de Symfony. De plus, Railway peut modifier le sous-domaine lors de redéploiements.

Solution : Variable d'environnement CORS_ALLOW_ORIGIN configurée comme regex dans Railway (^https://frontend-production-8a43\.up\.railway\.app$). NelmioCorsBundle lit cette variable à l'exécution, permettant une configuration dynamique sans rebuild.

Problème 2 - Clés JWT Perdues entre Redéploiements

Symptôme : Tous les utilisateurs étaient déconnectés à chaque redéploiement de l'application en production.

Cause : Les clés JWT RSA sont générées au build time dans le Dockerfile (openssl genrsa 4096). Chaque rebuild génère de nouvelles clés, invalidant les tokens existants.

Solution : Comportement documenté et accepté pour le MVP (déploiements rares, usage professionnel). La solution long terme serait de stocker les clés RSA dans un secret Railway et de les monter au démarrage plutôt que de les générer.

Problème 3 - Variables d'Environnement Telegram/Gemini Non Définies

Symptôme : Le conteneur Docker backend plantait au démarrage avec Environment variable "TELEGRAM_BOT_TOKEN" is not defined, même quand la fonctionnalité Telegram n'était pas utilisée.

Cause : services.yaml injectait ces variables dans tous les services via la section bind de Symfony, rendant leur présence obligatoire au démarrage du container, même si les services associés ne sont pas activés.

Solution : Déclaration de valeurs par défaut vides dans la section parameters de services.yaml :

parameters:
    telegram_bot_token: '%env(default::TELEGRAM_BOT_TOKEN)%'
    gemini_api_key: '%env(default::GEMINI_API_KEY)%'

Problème 4 - Doublement du Suffixe _test dans la CI

Symptôme : La CI échouait avec FATAL: database "calendria_test_test" does not exist

Cause : DATABASE_URL contenait déjà calendria_test dans le workflow GitHub Actions. Symfony ajoute automatiquement le suffixe _test quand APP_ENV=test, ce qui donnait calendria_test_test.

Solution : DATABASE_URL pointe vers la base calendria (sans suffixe) - Symfony ajoute _test → connexion à calendria_test. Le service PostgreSQL du CI crée donc la base calendria_test directement.

Problème 5 - Port Mismatch sur Railway

Symptôme : L'application backend répondait en local mais retournait 502 Bad Gateway sur Railway.

Cause : Railway utilise une variable d'environnement dynamique $PORT pour exposer le conteneur sur un port aléatoire. La configuration nginx du Dockerfile était hardcodée sur le port 8080, mais Railway attendait que le conteneur écoute sur $PORT.

Solution : Le script entrypoint.sh lit la variable $PORT au démarrage et réécrit dynamiquement la configuration nginx via sed avant de lancer supervisord :

PORT=${PORT:-8080}
sed -i "s/__PORT__/${PORT}/g" /etc/nginx/conf.d/default.conf
exec /usr/bin/supervisord -c /etc/supervisord.conf
